# Event-based architecture

분산 환경에서의 메시지를 통한 협력은 두 축으로 분류할 수 있다.
- 첫 번째 축: 시간적으로 결합되어 있는가 (temporal coupling)
- 두 번째 축: 참조적으로 결합되어 있는가 (referential coupling)

첫 번째 축. 시간적으로 결합되어 있다면 메시지를 보내는 쪽과 받는 쪽은 동시에 실행되고 있어야 한다. REST API가 대표적 예시다. 시간적으로 분리되어 있다면 메시지를 보내는 쪽과 받는 쪽이 동시에 존재할 필요가 없다. mailbox가 대표적 예시다.

두 번째 축. 참조적으로 결합되어 있다는 건 메시지 발신자와 수신자가 서로에 대해 알고 있다는 것이다. 대부분의 direct message가 이 유형이다. 반대로 참조적으로 분리되어 있다는 건 발신자와 수신자가 서로를 모른다는 뜻이다. Event-based 협력이 이 유형이다. 대표적으로 Kafka가 있다.
이론적으로 event-based 방식은 참조적으로 분리되어 있고 시간적으로는 결합되어 있는 방식을 뜻하지만, 현실적으로는 메시지 브로커가 message queue를 저장하고 있음으로써 시간적으로도 분리된 방식이 된다(예: Kafka).

# Publish-Subscribe pattern

다음 세 요소로 구성된 패턴이다.
- Publisher: 이벤트를 발행
- Subscriber: 관심사를 등록
- Broker: 발행된 이벤트와 관심사를 매칭해서 전달

구독 방식은 크게 두 가지다.
- Topic-based: 이벤트마다 topic이 있고, subscriber는 이 topic을 구독. 표현력이 낮지만 단순하고 빠름.
- Content-based: 이벤트의 속성값에 대한 조건으로 구독. 비용 큼(특히 분산 환경에서).

브로커 구성도 여러 종류로 나눌 수 있다.
- 중앙 집중형 브로커: 구성이 쉽지만 병목이나 SPOF 생김.
- 분산 브로커: 확장성이 좋지만 일관성 관리 복잡함.
- 피어 기반(gossip): 브로커 없이 노드끼리 P2P로 전파.

분산 환경에서 달성하기에 바람직한 속성들
- 전달 보장: at-most-once, at-least-once, exactly-once
- 순서 보장: 전체 순서 보장은 비싸므로 보통 partition 내 순서 보장
- 영속성: 이벤트를 보관하여 시간이 지나도 subscriber가 받아볼 수 있도록 할지
- 보안: publisher와 subscriber가 서로를 몰라서 접근 권한 관리가 까다로움

# Log as a unifying abstraction

- Kafka의 창시자 Jay Kreps가 쓴 글 *The Log: What every software engineer should know about real-time data's unifying abstraction* 에서 유래
- 추가만 가능하고 순서가 정해진 레코드 시퀀스, 즉 log라는 하나의 단순한 자료구조가 DB, 분산 시스템, 스트림 처리의 공통 기반이 될 수 있다는 뜻

로그 <-> DB(테이블)
- 로그를 처음부터 재생하면 -> 테이블
- 테이블의 변경 내역을 기록하면 -> 로그
- 즉 테이블은 로그의 특정 시점 스냅샷이며 로그는 테이블의 변경 이력임

로그 <-> 분산 시스템(합의 알고리즘)
- 분산 노드끼리 합의에 도달했다 == 로그가 같은 순서로 기록되어 있다 (예: 블록체인)

로그 <-> 스트림 처리
- 유명한 데이터 처리 아키텍처로 Lambda 아키텍처가 있다. 
- Lambda 아키텍처는 데이터를 두 경로로 동시에 처리하는데, batch layer와 speed layer다. Batch layer는 전체 데이터 스냅샷을 배치 작업으로 주기적으로 처리하는 것이고, speed layer는 그 이후의 변경사항을 stream으로 처리하는 것이다. (익숙한 패턴일 것이다)
- 데이터를 log로 본다면 모든 데이터 처리는 stream 처리가 된다. 전체 데이터를 처리하는 건 결국 첫 로그부터 시작해 전체 로그를 처리하는 거랑 같으니까. 이걸 Kappa 아키텍처라고 한다.
- 물론 이건 이론적인 모델이고, 실제로는 위의 Lambda 아키텍처가 많이 쓰인다(효율적이니까).
- 하지만 Kappa 아키텍처의 사고방식은 Flint 같은 현대적인 데이터 처리 프레임워크에 깊게 반영되어 있다.
